tryarch

How it works

tryarch runs a real x86_64 Linux guest in this tab and hands it official Arch packages — current ones from the mirrors, older ones from the Arch Linux Archive. There is no server. What follows is what that machine is, where the bytes come from, what is checked, and what it cannot do.

Boot

The page fetches a kernel, an initramfs and a resumable QEMU snapshot, then runs qemu-wasm in a worker. The packages you pick are downloaded and unpacked into the browser's own in-memory filesystem and handed to the guest over virtio-9p as /share, which the guest's init dresses up as an Arch root — /usr, /lib, /etc and a shell on PATH. Resuming the snapshot skips the kernel's start-up, so the prompt arrives in seconds rather than a minute.

Sources

Current packages come from the five Arch mirrors that allow cross-origin reads — mirror.lcarilla.de, archlinux.mailtunnel.eu, repo.c48.uk, mirror.iusearchbtw.nl and yonderly.org — tried in that order, with the repository database from the same place. Older versions come from the Internet Archive's mirror of the Arch Linux Archive, one item per package name, read through archive.org's CORS endpoint.

A recipe's sources are gathered by the page, since the machine has no network, and only a host that allows cross-origin reads can be read: raw.githubusercontent.com, crates.io and the npm registry do; GitHub release assets, GitLab, PyPI, gnu.org, kernel.org and SourceForge do not. A file the page cannot fetch is a row with a link and a place to drop the file. AUR recipes are read from GitHub's mirror of the AUR, because aur.archlinux.org sends no CORS headers either.

That mirror stops around October 2024. A version that was still current then, or older, is there; a version that came and went after that date is not, and archive.archlinux.org — which does have it — sends no CORS headers, so no page can read it. Those versions are missing from the version list altogether, not listed and unbootable: the list is what the archive holds, plus whatever is current now.

Integrity

A package from a mirror is verified against the SHA-256 in the repository database; a package from archive.org against the SHA-1 in its metadata. PGP signatures are not checked — the database and the package come from the same host, so the hash proves the transfer, not the packager. What runs is a guest in your tab with no network and no access to your machine, which is what makes that a reasonable trade here and not in a package manager.

Limits

  • .INSTALL scriptlets are never run, so a package that needs post-install work (users, caches, systemd units) arrives unconfigured.
  • Only packages present at boot get their /etc copied into the guest; anything added later keeps its files under /share/etc.
  • AUR packages and PKGBUILDs are built in the machine by makepkg, at emulator speed, with makepkg alone or with gcc — no base-devel, no VCS sources, no test suite, and nothing that fetches while it builds, which rules out most of the AUR. The Build lane is hidden for now; a link with aur= or pkgbuild= still reaches it. A -bin or any package takes under a minute, a C program many. pkglint grades the recipes themselves.
  • multilib is skipped; only x86_64 and any packages.
  • The unpacked tree lives in memory: about 1.2 GB of files at most, with 512 MB of RAM in the guest.
